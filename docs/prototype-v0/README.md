# 时迹 Timetrace（暂定名）· 桌面客户端设计原型

**定位：统一读取各类 LLM 编码工具的本地会话日志，统计一个需求的时间花在哪。** 新增一个工具 = 新增一个数据源（适配器 + 目录）。

> 名字暂用「时迹 / Timetrace」作占位，尚未定稿，也未查商标/重名。

静态 HTML/CSS/JS，无构建、无后端。直接打开 `index.html`（或 `a.html` / `b.html`）。数据全在 `mock.js`。

## 文件

| 文件 | 作用 |
|---|---|
| `index.html` | 入口，选方向 |
| `a.html` + `a.css` | 方向 A：仪器台 |
| `b.html` + `b.css` | 方向 B：留白 |
| `tokens.css` | **阶段色板与图案**（两个方向共用） |
| `base.css` | 结构与组件（两个方向共用，靠 CSS 变量分化） |
| `common.js` | 全部交互与渲染 |
| `mock.js` | mock 数据 |

URL 参数（便于截图/评审）：`?r=r2`（选中需求）`&theme=light|dark|auto` `&s=normal|partial|error|empty` `&view=settings` `&today=1` `&drawer=1` `&zoom=12` `&split=1` `&manage=1` `&rename=1` `&proc=1&turn=5`（过程视图，turn 为轮序号）`&src=jsonl|langfuse`（过程视图数据源）。
右上角也能切换"原型状态"和主题。

mock 需求：`r1` 正常（46 轮）、`r2` 很长（320 轮、5 会话、32 段空闲）、`r3` 很短（3 轮）、`r4` 进行中、`r5` 带解析警告、`r6` 18 轮、`r7` 空数据（0 轮）、`r8` 等我很多、`r9` 12 轮。

## 设计方向

**A 仪器台**：等宽字体、直角、1px 细线、行高 28px，时间轴 44px 高带刻度网格，阶段明细是带表头的表格，指标是两格"读数"。信息密度最高，1280×800 下左栏能放 9 个需求、右栏一屏看到指标+占比+时间轴+前 8 段明细。

**B 留白**：无衬线、圆角、行高 ~60px（两行：名称+时长 / 迷你条 / 次要指标），时间轴 28px 细带，阶段明细是分组卡片列表（无表头）。同样的数据密度下要多滚动，但扫读更轻松。

两者**信息结构完全一致**，选哪个主要是气质选择。选定后另一个可删。

## 阶段色板

色相取自 Okabe-Ito 色盲友好色板，浅色下加深以保证相对白底 ≥3:1（图形对象标准）。**颜色之外同时有填充图案 + 单字母标签**，灰度打印或色盲下也能区分。

| 阶段 | 字母 | 浅色 | 深色 | 图案 |
|---|---|---|---|---|
| 聊方案 | P | `#0072B2` | `#4DA3E0` | 纯色 |
| 调研 | R | `#00916A` | `#2FC79A` | 45° 斜线 |
| 写代码 | C | `#C77C00` | `#F0A93A` | 圆点 |
| 改代码 | F | `#C8321E` | `#F26A55` | 交叉网格 |
| 测试 | T | `#B5559A` | `#E08FC0` | 横线 |
| 其他 | O | `#6B7686` | `#98A3B3` | 竖线 |
| 等我（非阶段） | W | `#9C8A00` | `#E8DA45` | 棋盘格 |
| 空闲（不计入） | – | 无填充 | 无填充 | 虚线框 / 斜线底纹 |

规则：
- 「写代码」与「改代码」是最需要区分的一对（返工统计的核心），所以选了色相差最大的橙/红，**再加上点 vs 网格**两种相差明显的图案。
- 「等我」用 Okabe-Ito 的黄色，单独保留给它，不给阶段使用，这样"AI 在等我"在任何图里都一眼可见。
- 格子宽度 ≥16px 显示字母，<6px 退化为纯色（图案在这个尺寸只会产生摩尔纹），放大后恢复。
- 浅/深色靠 CSS `light-dark()` 跟随系统，`html[data-theme]` 可手动覆盖。
- 未做对比度自动化测试；上述数值是按 WCAG 图形对象 3:1 目测+手算选取，建议实现时用工具复核。

## 多工具与扩展机制（新增）

### 核心思路：适配器 + 统一数据模型

每个工具的日志格式不同，但客户端只认一套统一模型。**适配器**负责把某个工具的原始日志翻译成它：

```
原始日志（各工具不同）  →  适配器  →  统一模型 Session / Turn / Span  →  阶段分类  →  需求聚合  →  界面
```

界面和统计层**完全不知道**日志来自哪个工具，只关心：①统一模型的字段，②适配器声明的**能力**（哪些字段它能提供）。

### 数据源 = 适配器 + 目录

设置页「数据源」：一行一个，勾选启用，可移除；右侧显示已发现文件数。**添加数据源**：选适配器 → 选目录 → 「测试扫描」（先试跑，显示识别到几个会话/轮、能提供哪些字段、有几行解析失败）→ 确认添加。同一个适配器可以有多个目录（如另一块磁盘）。

### 三层扩展方式（由易到难）

| 层 | 怎么接入新工具 | 适用 | 状态 |
|---|---|---|---|
| ① 内置适配器 | 选目录即用，默认路径自动检测 | 主流工具（Claude Code、Codex CLI、Gemini CLI…） | 原型已做界面 |
| ② 声明式适配器（YAML） | 写一个 YAML：用 JSONPath 把 时间戳 / 角色 / 文本 / 工具名 / 工具参数 / usage 映射到统一字段；放到 `~/.config/timetrace/adapters/` | 任何 jsonl / json 型日志，**不用写代码** | 原型已做"自定义适配器"流程 |
| ③ 可执行插件 | 一个可执行文件：输入日志路径，输出统一格式的 NDJSON | 二进制/数据库/奇怪格式 | **建议 v1 不做**，只在文档里预留约定 |

**推荐：v1 做 ①+②。** 理由：大多数新工具的日志是 jsonl，用 YAML 映射就能接入，用户自己加不用等发版；③ 引入"执行外部程序"的安全和分发问题，收益小。代价：YAML 映射表达不了"需要跨多行关联"的复杂格式（比如工具调用和结果分在两条记录且靠 id 配对），这类要在映射里提供 `join` 语法或留给 ③。

### 统一模型（适配器的输出）

| 实体 | 字段 |
|---|---|
| Session | `id` `tool`（适配器 id）`title?` `file` `startedAt` |
| Turn | `sid` `t`（我的 prompt 时间）`dur`（AI 工作秒）`gap`（到下一轮的秒数）`running?` `prompt` `reply?` `tools[]` `spans[]?` |
| Span（可选） | `k`（llm\|tool\|perm\|agent）`name` `arg` `off` `dur` `ok` `depth` `out?` + LLM 的 `model` `tin` `tout` `cache` `stop` `ttft?` `cost?` |
| 阶段 `phase` | **不由适配器给**，由「阶段规则文件」基于 tools / 文本分类；人工可覆盖 |

必须字段只有 `t` / `dur` / `gap` / `sid`，其余都是可选。适配器**只需声明它能填哪些字段**，缺了就缺。

### 能力声明与"不编造"原则

每个适配器声明能力：`时间戳 · 工具调用 · token · 子代理 · 权限等待 · 首 token · 成本`。设置页有「适配器能力」矩阵；过程视图顶部显示当前会话数据源的能力芯片（✓ / –）。**缺失的字段在界面里一律显示灰色「–」并说明原因，不估算、不补零。** 同一个需求里混合多个工具的会话是允许的（例如先在 Claude Code 聊方案，再用 Codex 实现），汇总时只统计双方都有的字段。

Langfuse / OTel 是**叠加来源**而不是独立适配器：为已有适配器补充"权限等待、首 token、成本"并把轮内耗时从推算变为实测。目前只对能导出 OTel 的工具（Claude Code）可用，其余工具的 Langfuse 选项置灰。

### 界面上的体现

- 左栏每个需求带工具徽标（`CC` `CX` `GM` …，一个需求可含多个）；顶部新增「全部工具 / 某个工具」筛选。徽标只用文字+描边，**不占用颜色**，颜色仍专属于阶段。
- 详情页副标题写出该需求涉及的工具；会话列表每行带工具徽标。
- 今日概览多一块「按工具」的时长。
- 空状态：列出所有内置工具的默认路径检测结果（均「未找到」），每个工具一个「选择目录…」；另有「添加自定义数据源…」。
- 解析失败：每条错误前带工具徽标，便于判断是哪个适配器出的问题。

> 注意：mock 里各工具的默认路径与能力是**示例**，没有逐一核实这些工具真实的日志位置和格式。接入前每个适配器都要拿真实日志验证。

## 过程视图（新增）

回答"这个会话里，一轮对话内部时间花在哪"。入口三处：详情头部「过程」、会话列表每行的「过程」、对话抽屉的「过程」。`Esc` 返回。

- 顶部：会话选择、数据源标签、会话级汇总（LLM 耗时 / 工具耗时 / 权限等待 / 工具失败 / token / 成本）。
- 轮次条：该会话每一轮一格，沿用阶段色与图案；底部黑条 = 该轮有工具失败。
- 瀑布图：选中一轮后，每行是一个 span（LLM 请求 / 工具 / 等权限 / 子代理），条的位置与宽度 ∝ 该轮内的偏移与耗时。子代理内部调用缩进一级；失败的 span 有红框 + ✕。进行中的最后一个 span 脉动。
- 右侧：选中 span 的详情（耗时、状态、模型、token、缓存、停止原因、输入输出）。
- 键盘：`←→` 换轮，`↑↓` 选 span，`[` `]` 换会话。
- span 种类用**字母 + 形状**区分（L/T/A/W），颜色只做辅助；"等权限"沿用「等我」的黄色棋盘格，因为本质也是在等我。

**数据源差异（右上角可切换，用来评估解析层能提供什么）**

| 字段 | 本地日志 | Langfuse（OTel span） |
|---|---|---|
| 轮内每个 LLM / 工具的耗时 | 由消息时间戳推算（工具较准，LLM 为近似） | 实测 |
| 等权限确认 | **无法区分**，并入随后的工具耗时 | 独立 span |
| token / 缓存 | 有（assistant 消息的 usage） | 有 |
| 首 token 时延 | 无 | 有 |
| 成本 | 无（可按单价自行估算） | 有 |
| 进行中的最后一轮 | 有（文件持续追加） | hook 方式没有；OTel 方式有 |

注意：mock 里 `perm`（等权限）目前**计入「AI 工作」**，没有拆出到「等我」。这是个待定的口径问题，见文末"待确认"。

## 时长格式（全局统一）

`≥1h → 1h05m`、`<1h → 12m`、`<1m → <1m`；仅单轮级别（提示、抽屉）额外显示秒：`2m05s`。所有数字用等宽字体 + `tabular-nums`。

## 时间轴的缩放方案（核心）

问题：几百轮对话，一屏放不下，且夹杂数小时的空闲。方案是**五个机制叠加**，全部可在 `?r=r2` 的 320 轮会话里操作：

1. **两种横轴**：「按轮」每轮等宽；「按时间」宽度 ∝（AI 工作 + 等我）。「自动」= 超过 120 轮用按时间，否则按轮。
2. **折叠空闲**（默认开）：每段空闲折叠成一个固定宽度的虚线块（宽度随个数自适应，8–30px），不按时间缩放，否则一个 8 小时的空闲会把整条轴吃掉。点单个虚线块可展开成 84px 并写出时长；也可整体关闭折叠。
3. **缩放**：`−` / `适应` / `+`、键盘 `-` `+` `0`、`Ctrl+滚轮`（以光标为锚点）。`适应`= 整条正好放进宽度。放大到格子 ≥16px 时出现阶段字母。
4. **小地图**：时间轴上方 16–18px 的整体缩略，带可拖动的视口框；点击小地图任意位置跳转。放大后才出现。
5. **窄格合并**：<5px 的相邻同阶段轮合并为一块（悬停显示"第 a–b 轮 · N 轮 · 时长"），放大后自动拆开。

其他：
- 每格右端的黄色棋盘格 = 该轮之后"等我"的时间占比。
- 悬停：单轮显示摘要 + 我的 prompt 首句；合并块显示聚合信息。
- 点击格子：打开抽屉并定位到该轮。悬停下方明细行会虚线高亮对应的格子。
- 进行中的最后一轮轻微脉动（`prefers-reduced-motion` 下关闭）。
- 空闲阈值在设置里调，时间轴和指标**实时重算**（空闲/等我由 `gap` 与阈值推导，不是预存的）。

## 需求管理：合并 / 拆分

选了"**多选 + 按钮**"，没做拖拽。理由：① 需求列表很长、会滚动，拖拽跨屏容易误放；② 拖拽没有键盘等价操作；③ 拆分的对象是"轮"，要在时间轴上选切点，点击比拖拽自然；④ 都带撤销提示条，操作可逆。

- **合并需求**：左栏「管理」→ 勾选 ≥2 个 → 「合并所选」。结果取最早的需求名。
- **按会话拆分**：详情底部"会话"列表勾选会话 → 「拆为新需求」（不能拆走全部）。
- **按轮拆分**：详情右上「按轮拆分」→ 点时间轴上的一格作为新需求的第一轮 → 确认。适用于一个会话里混了两件事。
- **改名**：详情标题旁「重命名」、双击标题或 `F2`；`Enter` 保存 `Esc` 取消。
- 抽屉里改阶段：只改该段，标记"手动"，可撤销。

## 键盘

`↑↓` 切换需求（焦点在左栏）→ `Enter` 进入阶段明细 → `↑↓` 选段、`←→` 选轮 → `Enter` 打开抽屉 → 抽屉内 `[` `]` 换段、`1–6` 改阶段 → `Esc` 关抽屉，再 `Esc` 回左栏。`/` 搜索，`F2` 改名，`+ - 0` 缩放时间轴。

## 960 宽

左栏收窄到 280–300px；图例改两列；明细表隐藏"起止"列；<820px 隐藏左栏（原型未做抽屉式导航）。

## 有意不做的

- 不画图表库式的饼图/趋势图。需求是"时间花在哪"，一条堆叠条够用；趋势、周报留给以后。
- 不做拖拽合并/拆分（见上）。
- 不做多窗口 / 托盘真实弹出：今日概览用 340px 面板模拟，位置在右上。
- 不做移动/窄屏适配（桌面工具）。
- 不做阶段规则的可视化编辑器：设置里只有文件路径 + 校验按钮。规则调整用改文件。
- 不做跨会话的 span 聚合分析（哪个工具最慢、哪类失败最多）；过程视图只看单个会话。
- 不展示完整原始对话/完整 diff：抽屉只给 prompt、回复摘要、工具调用列表。
- 不做"目标/预算"之类的管理功能。
- 主题切换只有 跟随系统 / 浅 / 深，没有自定义强调色。

## 已做的假设（请核对）

1. **活跃 = AI 工作 + 等我**；空闲不计入。阶段占比条 = 6 个阶段（按 AI 工作时间）+ 等我，加起来等于活跃。
2. 「等我」= 一轮结束到我下一条 prompt 之间，且小于空闲阈值；≥ 阈值记为空闲。**最后一轮之后不算等我**（没有下一条）。
3. 阶段明细合并规则：只按**阶段是否连续相同**合并，不看会话/空闲边界。
4. 阶段属于「轮」（一次 user prompt → assistant 完成），不是属于消息或工具调用。
5. 需求列表的时间范围筛选按需求的**结束时间**。

# 每个屏幕依赖的数据字段

> 用来核对解析层。「派生」表示可由其他字段前端计算，解析层不必直接提供。

### 通用：需求 `Requirement`
`id` · `name`（可被用户改）· `status`（active|done；active 来自最后一轮仍在进行）· `sessions[]` · `turns[]` · `warn`（可选，解析告警文案）· 手动合并/拆分/改名的持久化结果

### 通用：会话 `Session`
`id` · `tool`（适配器 id，决定徽标与能力）· `title`（可无，回退为序号或首条 prompt 前 N 字）· `file`（原始日志路径）

### 通用：轮 `Turn`（最关键）
| 字段 | 说明 |
|---|---|
| `t` | 开始时间（ms）= 我的 prompt 时间 |
| `dur` | AI 工作秒数 = 该轮最后一条 assistant 消息时间 − prompt 时间 |
| `gap` | 本轮结束到下一轮 prompt 的秒数；最后一轮为 null |
| `running` | 是否仍在进行（决定"进行中"标记与最后一轮的 `dur`） |
| `phase` | 阶段（6 选 1），由规则文件分类；允许人工覆盖 |
| `manual` | 阶段是否被手动改过 |
| `sid` | 所属会话 |
| `summary` | 一句话摘要（明细、悬停用） |
| `prompt` | 我的 prompt（可截断） |
| `reply` | AI 回复摘要 |
| `tools[]` | `{name, arg 摘要, ok}` |

### 1. 主窗口 · 左栏需求列表
需求名 · 涉及的工具（派生：会话的 `tool` 去重）· 总活跃（派生：Σ dur + Σ 等我）· 各阶段耗时（派生）· 等我时长（派生）· 改代码占比（派生）· 轮数 · 结束时间（时间范围筛选）· `status` · `warn`

### 1. 主窗口 · 右栏需求详情
- 指标：活跃 / 等我 / 最长一次等我 / 空闲总时长与段数（均派生自 `dur` `gap` 与阈值）
- 阶段占比与图例：各阶段秒数（派生）
- 时间轴：每轮 `t` `dur` `gap` `phase` `running` + `summary` `prompt`（悬停）；起止时间；空闲段由 `gap ≥ 阈值` 推导
- 阶段明细：连续同阶段合并后的 `phase`、首轮 `summary`、轮数、时长、起止时间、`manual`
- 会话列表：`sessions[].title/file`、每会话的轮数与活跃时长（需 `turn.sid`）

### 2. 对话抽屉
段内所有轮的 `t` `dur` `gap` `prompt` `reply` `tools[]`（含 `ok`）；写入：修改段内各轮 `phase` 并置 `manual`（需要可写的覆盖层，不改原始 jsonl）

### 3. 需求管理
合并：多个需求的 `sessions` + `turns`；拆分：按 `sid` 或按 `turn` 序号切；改名：`name`。三者都要求解析层有**不改原始 jsonl 的持久化覆盖层**（需求 ↔ 会话/轮的映射表），且能撤销。

### 4. 今日概览
今天（本地时区 0 点起）的各轮 `t` `dur` `gap` `phase`（跨天的轮需决定如何截断）· 进行中需求的当前轮 `phase` 与已运行时长 · 今日各需求的活跃时长

### 过程视图
- 会话内每轮：`turn.sid` `turn.phase` `turn.dur` `turn.running`（轮次条与标题）
- 每轮的 `spans[]`：`k`（llm|tool|perm|agent）· `name` · `arg` · `off`（相对该轮开始的秒数）· `dur` · `ok` · `depth`（子代理内部为 1）· `out`（输出摘要，可截断）
- LLM span 额外：`model` `tin` `tout` `cache` `stop`（必有）；`ttft` `cost`（仅 Langfuse，jsonl 缺失时界面置灰）
- 数据源标识：`source`（jsonl | langfuse），每个需求/会话一个
- 若走 Langfuse：session_id ↔ 会话；trace ↔ 轮；observation ↔ span；读取用 v2 observations 接口 + sessionId 过滤 + 时间范围

### 5. 设置页
数据源列表：`{适配器 id, 目录, 已发现文件数, 是否可读, 是否启用}` · 适配器能力表（`ts tools tokens sub perm ttft cost` 各 ✓/–）· 添加数据源时的「测试扫描」结果（文件数、会话数、轮数、字段映射校验、跳过的行）· 空闲阈值（分钟）· 需求聚合时间窗（小时）· 阶段规则文件路径 + 校验结果（阶段数、规则数、冲突）

### 6. 空状态 / 解析失败
各内置适配器的默认路径检测结果（找到/未找到）；解析错误列表 `{tool, file, line, reason}`；文件总数与失败数 · 部分失败时每个需求的 `warn`（跳过的行数、会话、行号）

### 今日概览（补充）
按工具的今日时长（派生：轮 → 会话 → `tool`）。

### 解析层需要特别确认的点
0. **每个目标工具的真实日志位置与格式**（mock 里的路径是示例）：是否有时间戳到秒、能否区分 user prompt 与工具结果、有无 token usage、是否一个文件一个会话。能力矩阵要以真实情况为准。
1. 能否可靠得到每轮的 `dur`（一轮最后一条 assistant 消息时间）？含 sub-agent / sidechain 时怎么算？
2. 正在写入的 jsonl（进行中会话）末行可能不完整，需要容错而不是整文件失败。
3. `summary` / `reply` 摘要从哪来：截取原文，还是本地规则/模型生成？
4. 跨天的轮和空闲段，今日概览如何截断。
5. **轮内的"等权限确认"算 AI 工作还是等我？** 现在 mock 算 AI 工作；更合理的是单独拆出，计入「等我」。jsonl 里区分不了（见上表），只有 OTel 能做到。
6. 子代理（Task）的内部调用在 jsonl 里是 sidechain 消息；它们的耗时是否应计入父轮的 AI 工作（现在是，且不重复计算）？
7. 手动覆盖层存哪、会话文件新增轮次后如何与覆盖层对齐（建议以 sessionId + 轮的 prompt uuid 为键）。

## 洞察（Dashboard）

- 入口：顶栏「洞察」，`?view=dash&range=7|30|all`。Esc 返回。
- 结构：①「最耗时的部分」大卡（阶段名 + 时长 + 占比 + 较上期变化）与 4 个 KPI；②建议卡（最多 4 条，按涉及时间排序）；③阶段排名（含较上期变化）；④最近 14 天堆叠柱；⑤最耗时需求 Top5（点击跳到该需求）。
- 建议是本地规则，不调用模型、不上传数据；每条给出数字依据、2–3 个可做的动作、可跳转的相关需求。规则与阈值放在规则文件里可改。
- 目前的规则：改代码 ≥25%；聊方案 <6% 且改代码 ≥20%（明确标注为相关性）；等我 ≥15%；调研 ≥18%；单轮 >10 分钟的轮数 ≥3。
- 「较上期」只在 7/30 天范围出现；上期无数据时不显示，避免误导。
- 未做：权限等待的建议（本地日志里无法分离，只有 Langfuse 数据源可做）；跨周期基准线（没有可信的"正常值"，不编造）。

## 建议生成：规则 / 大模型（可选）

- 两层：**规则永远可用**（本地、不联网）；用户在 设置 → 建议生成 里配置了模型，洞察页才出现「用模型生成」。未配置时洞察页只提示一行「配置模型（可选）」。
- 触发方式：手动点击才发请求，不自动、不后台调用；换时间范围/改配置后结果作废，回到规则建议。
- 失败处理：模型出错（Key 无效、超时等）→ 红框提示原因 + 自动显示规则建议 + 「重试」，用户不会看到空白。
- 来源标识：建议区标题旁始终有徽标「规则生成 / 模型 · 模型名」；模型结果底部写耗时、token、发送范围，并注明「请自行核对数字」；折叠区「对照规则建议」可对比。
- 隐私分三档（默认最小）：只发聚合数字（需求以「需求A/B」代称）/ 加需求名 / 再加每段摘要。设置页可展开预览**将要发送的 JSON**；选本地 Ollama 数据不出本机。Key 存系统钥匙串，不写配置文件。
- 服务：Anthropic / OpenAI 兼容接口 / 本地 Ollama（模型名、地址均可改，不预设具体型号）。
- 原型里模型输出是按数据拼出的**示例文本**，不是真实调用；URL 参数：`adv=llm`（已配置）、`advs=loading`、`fail=1`（点生成后模拟失败）、`send=agg|names|summ`。
- 模型的任务边界：只做「解读 + 给动作」，所有数字由本地算好后传入，提示词要求不得编造数字（待实现时写进系统提示）。
